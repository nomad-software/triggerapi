# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TriggerAPI is a desktop client for making REST API and gRPC calls, inspired by Postman. It is written in Go with a Qt 6 GUI via the [miqt](https://github.com/mappu/miqt) bindings.

REST and gRPC requests, environments and saved requests in folders are implemented; history is not started yet.

## Compatibility of saved files

Every change must stay backward compatible with existing request files (`requests.json`). A file written by any earlier version must load with nothing lost, and nothing the format or the UI already allows may be taken away unless the user asks for it. Add new data as optional fields (`omitempty`), or in a section or file of its own, so that a file without it reads and writes as before. Normalise old shapes when loading rather than rejecting them, and give every change to the format a test that loads a file in the old format. Check the git history before deciding that something was never supported. The handling of old formats stays, cruft or not, until the user decides to settle on a cleaner format once the program is mature.

## Architecture

Packages under `internal/`; only `ui` depends on Qt.

- `rest` is the HTTP engine. `rest.Request` holds everything in the request UI (method, URL, params, headers, auth, body type, raw body, form fields), including fields the chosen auth/body type does not use, so it round-trips through JSON without loss. `Request.Build` turns it into an `*http.Request` and `rest.Send` returns a `rest.Response`. `Request.Options` (a time limit and whether redirects are followed) says how it is sent and is not saved with it: the caller sets it, and `Send`, `Curl` (`--max-time`, `--location`) and `RunCurl` go by it; a request that takes too long fails with `context.DeadlineExceeded`. Put request-building rules here (default scheme, param ordering, header precedence) so they stay unit-testable.
- `env` holds environments (named sets of variables). `Environment.Expand` substitutes `{{name}}` placeholders, leaving unknown ones untouched. A variable whose whole value is a call of a built-in function (`random_uuid()`, `iso_date(n)`, `iso_timestamp(n)`, `unix_timestamp(n)`, in `functions.go`) is given what `env.Evaluate` makes of it, afresh on each `Expand`; `Environment.Expander` / `Store.Expander` return a function which makes each such value once, so that it is the same in every part of one request. The functions are described in the README and nowhere in the UI. `Environment.Set` gives a variable a value, adding it if need be. A `Variable` has a `Description`, which is only for the reader; several variables can have one name, of which the last enabled one is used.
- `capture` takes a value out of the JSON of a response: `capture.Extract(document, path)`, where a path is names separated by dots with array indexes in brackets (`data.items[0].id`, `[-1]` for the last, `["a.b"]` for a name with a dot in it). Both `rest.Request` and `rpc.Request` have `Captures`, which are `capture.Rule`s: a variable name, a path and an optional regex (stored as `key`, `value` and `regex`), none of them expanded. `Rule.Extract` takes the value at the path and gives it to `capture.Match`, which keeps what the regex matches, or what its first group does if it has groups; a regex that is not valid or does not match is an error like any other. `capture.PathAt(document, offset)` goes the other way, from a place in a document to the path of the innermost value there (a member's name counts as part of its value), with the last name in the path to call it by.
- `rpc` is the gRPC engine, built on the connectrpc libraries (`connectrpc.com/connect` and `connectrpc.com/grpcreflect`) with `google.golang.org/protobuf` for dynamic messages. Do not add `google.golang.org/grpc`. `rpc.Reflect` asks a server to describe itself through server reflection and returns a `Schema` (there is no support for loading `.proto` files); `rpc.Invoke` sends one JSON message over a bidirectional stream and collects every response, which covers unary and server-streaming methods. A status other than OK, including a cancelled call, is returned as a `Response`, not an error. Calls are always made in the gRPC protocol (`connect.WithGRPC`); `Response.Protocol` names the protocol the server answered in, read from its `Content-Type` by `rpc.Protocol`, and is shown as the Protocol field. `rpc/rpctest` is a connect-based test server with an Echo service, used by the `rpc` and `ui` tests.
- `collection` holds saved requests: a `Store` of `Folder`s, each with `Request`s. A `Request` has a name, a `Type` (`rest` or `grpc`) and exactly one of an embedded `*rest.Request` (stored flat beside the name, which is also the format from before there were types) or `GRPC *rpc.Request`; `Load` normalises this. Check `Type` before touching either. A `Folder` holds requests and other folders, to any depth (`Folders` then `Requests`), and records whether it is shown closed (`Collapsed`), which the tree sets as folders are opened and closed, and whether it is a favourite (`Favourite`, only for a folder at the top level, written only when set so older files are unchanged, and cleared by `Store.MoveFolder` when the folder goes inside another); the store has only folders at its top level, never requests. Folders and requests are held by pointer so they keep their identity when others are removed.
- `openapi` turns an OpenAPI 3 or Swagger 2 document (JSON or YAML, read with `gopkg.in/yaml.v3`) into a `collection.Folder` of REST requests: one per operation, in subfolders by first tag. Unknown values become `{{placeholder}}`s. It is tolerant of missing references. An example body is made from a schema by an `exampleMaker`, which does not make a schema inside itself and stops at `maxValues`, as schemas that refer to one another would otherwise make an example of enormous size.
- `postman` does the same for a Postman collection (formats 2.0 and 2.1), keeping its folders, and leaving out scripts, saved responses and descriptions.
- `postman.ImportEnvironment` reads an environment exported from Postman into an `env.Environment`. The import button of the Environments tab (`envList.importDocument`) works like the one for requests, with its kinds in `envImportSources` (Postman alone for now) and the same `chooseSource`, `chooseFile` and `warn` hooks for tests; the imported environment becomes the selected one.
- The import button of the Requests tab (`requestTree.importDocument`) asks which of these to import with a `choiceDialog`, then for the file, and adds the folder to the top level with the folders inside it closed. The kinds are described in `importSources`. Tests replace `requestTree.chooseSource`, `chooseFile` and `warn` rather than let dialogs open.
- `workspace` keeps the workspaces, each of which has its own environments and requests. A workspace is a folder, named after it, inside the workspaces folder, holding `environments.json` and `requests.json` (`workspace.Environments` / `Requests` give the paths). The package lists, creates, renames and removes them, and checks names (`Valid`: usable as a folder name on any system, unique ignoring case). `Remove` deletes only those two files and then the folder, and refuses a folder with anything else in it. `Import` and `CopyAll` copy files in without replacing anything.
- `settings` holds state kept between runs: window size, maximised state, sidebar width, response height, the response body font (which the request body, the gRPC message and the curl command are shown in too), how long a request can take in seconds (`Timeout`, zero for no limit) and whether REST redirects are left unfollowed (`NoRedirects`), the JSON highlighting colours (empty means the theme default), the icon, button, placeholder and error colours (`settings.Colours`, empty means the default), the workspaces folder (empty means the default), the name of the workspace in use and the pinned requests. `Settings` holds a slice, so compare two with `reflect.DeepEqual`. It is loaded in `NewWindow` and saved from the window's close event and whenever the settings dialog is accepted.
- `crypt` encrypts the files of the workspaces with a pair of SSH keys, using age (`filippo.io/age` and its `agessh`), as armoured text. `crypt.Open` reads the keys from the files the settings name (`settings.PublicKey` / `PrivateKey`, paths which can start with `~`), asks for the passphrase of a private key that has one, once, and checks that they are a pair. A nil `*crypt.Keys` leaves data as it is and cannot read what is encrypted; it is what the settings file is read and written with, and the UI reads and saves no workspace with it. Data that is not encrypted (`crypt.Encrypted`) is read as it is by any keys, so files from before are still read. `crypt.Unusable` makes keys that fail everything, for keys the settings name which could not be opened, so that nothing is saved without them. `crypt/crypttest` makes key files for tests. The settings file is never encrypted.
- `jsonfile` does the atomic JSON load/save used by all of these; `LoadWith` / `SaveWith` take the keys (as do `env.LoadWith`, `collection.LoadWith` and the stores' `SaveWith`), and `Convert` has a file written with other keys, or none. What it writes can be read and written by the user alone (0600), as can what `workspace` copies; workspace folders are made 0700. `main.go` passes the default places as `ui.Files`: the settings file, which is `triggerapi/settings.json` in the system's configuration folder (`settings.Path`, from `os.UserConfigDir`: `~/.config` or `$XDG_CONFIG_HOME` on Linux, `~/Library/Application Support` on macOS), the workspaces folder, which is `triggerapi/workspaces` in the system's data folder (`workspace.DefaultDir`: `~/.local/share` or `$XDG_DATA_HOME` on Linux, `~/Library/Application Support` on macOS; `Window.workspacesDir` gives the folder in effect, as the settings can name another), plus where things used to be in the working directory: the `workspaces` folder (`Files.OldWorkspaces`) and the `environments.json` and `requests.json` from before workspaces. `settings.Prepare` makes the settings folder at startup. On a run that finds no workspaces, `Window.migrate` copies in the workspaces of the old folder (only when the default folder is in use), or failing that makes one named Default and copies those two files into it, leaving the originals alone.
- `ui` is the Qt layer, wired together in `NewWindow`:
  - The sidebar is a tab widget with a Workspaces tab (`workspaceList`), an Environments tab (`envList`) and a Requests tab (`requestTree`), which is the one selected at startup (`tabWorkspaces` / `tabEnvironments` / `tabRequests`). The selected workspace is the one in use: selecting another calls `Window.openWorkspace`, which closes the open request and the environment editor and loads that workspace's stores through `envList.load` / `requestTree.load` (`Window.loadWorkspace` reads them, and is also used at startup). Workspaces are added, renamed (in the list, which renames the folder; `Window.renamedWorkspace` then repoints the store paths) and removed after confirmation; the last one cannot be removed. Tests replace `workspaceList.confirm` and `warn`. Its tabs are down the left edge with icons and tooltips in place of text; Qt draws left-hand tabs rotated, so `drawTabIcon` counter-rotates the picture. The buttons of each tab are icons in a row along its bottom (`newIconButton` and `newButtonRow` in `tabbutton.go`, with the glyphs in `icons.go`), named in their tooltips: the colour of the icon of their tab (`colourEnvironments` / `colourRequests`), but for remove which is `colourRemove`, with import apart at the right. Removing an environment, a request or a folder that is not empty asks first (`confirm`). Each tab has a duplicate button: `workspace.Duplicate` copies a workspace's folder, `envList.duplicate` an environment, and `requestTree.duplicate` a request or a folder with everything in it (`collection.Request.Clone` / `Folder.Clone`). The copy is named after the original with " copy" added, is selected, and has its name opened for editing. Each owns its store and saves on every change; there are no Save buttons. If a file cannot be parsed at startup, saving to it is disabled so it is never overwritten.
  - `Window.stack` shows the REST request UI (`requestPanel` + `responsePanel`), the gRPC request UI (`grpcPanel` + its own `responsePanel`) or `envEditor` (`pageRequest` / `pageGRPC` / `pageEditor`). `Window.requestPage` picks the request page from the type of the open request.
  - Above the stack is a row of tabs (`requestTabs`, a `QTabBar` in `requesttabs.go`), hidden while the environment editor is open. There is a tab for each pinned request and at most one tab that is not pinned, which shows whichever request was last selected in the sidebar (`Window.openRequest` → `requestTabs.open`); selecting a pinned request goes to its tab. Each tab has a button before its name, and no icon of its own: a pin on the unpinned tab, which pins it; on a pinned tab the icon of the request's type, which becomes the red bin of the remove buttons, to unpin it with, while the pointer is over the tab (`requestTabs.hover`, fed by the tab bar's mouse move and leave events and the buttons' enter events). A tab unpinned while shown becomes the unpinned tab, otherwise it closes. The tabs do not have a request UI each: they all show their request in the one UI (`Window.showTab` calls `Window.show`), so switching tabs is like selecting in the sidebar, and cancels a request in flight. A tab keeps what would otherwise be lost: the response its request was last given (`requestTab.replay`, set by `Window.run`) and, for the unsaved request, what had been typed (`requestTab.draft`, kept by `Window.stash`). Choosing a tab selects its request in the tree (`requestTree.selectRequest`). Pinned requests are saved in the settings as `settings.Pin`s, a workspace name and the path of names from `collection.Store.Path`; `Window.keepPins` records them on close and before leaving a workspace, and `Window.restoreTabs` reopens them (`Store.Find`) at startup and on entering a workspace, showing the first.
  - Both sidebar lists are kept in alphabetical order, ignoring case, by sorting the stores themselves (`env.Store.Sort`, `collection.Store.Sort`; folders still come before requests) on load and after every add, rename, move and import, then redrawing. In the request tree a redraw replaces every item, so never keep a `QTreeWidgetItem` across an operation that can redraw; a rename made in the tree is sorted a turn of the event loop later.
  - Nothing can be renamed to an empty name. A request or folder whose name is emptied in the tree is given back the name it had, and nothing is saved. The environment editor keeps the name the environment has (`envEditor.named`) while its field is empty, as it has to be on the way to another being typed, and puts it back in the field when editing there is finished. A workspace is refused one by `workspace.Valid`.
  - The selected environment is the active one. Edit opens it in `envEditor`, which follows the selection while open and reports edits through `envList.update`. Edit puts the keyboard in the name field with the name selected (the `onEdit` set in `NewWindow`); following the selection does not. F2 in a list or the tree of the sidebar does what its rename button does, or for an environment its edit button.
  - Clicking a request in the tree opens it (there is no button for it): `Window.open` points at it, its tab names it (nothing in the request UI does), `Window.updateHeaders` fills the `environmentSelector` (a line of its own above the request tabs, at the right, so the tabs have the whole width: a labelled drop-down of the workspaces and one of the environments, each as wide as its longest name where the window has the room and squeezed, down to `selectorMinWidth`, where it has not, so that a name never makes the window wider, which select the workspace and the active environment by selecting them in the sidebar lists, and a button with the globe of the environments which does what the edit button of the Environments tab does and is disabled when no environment is selected; it is outside the request UIs because both are the same for every tab, and `workspaceList.onList` has it filled again whenever the workspaces are listed), `requestPanel.load` shows it, and every edit (`requestPanel.onChange`) is written back with `requestPanel.request()` and saved. With `Window.open == nil` the REST request UI holds an unsaved request. Add Request asks for the type through `askRequestType`, a package variable that tests replace; by default it shows a `choiceDialog` (`choice.go`), the generic pick-one-of-these dialog that offers each choice as an icon with its name beneath, and which the import dialog also uses. Icons, including the program's own (`appIcon`, used as the window icon and so shown in the about box), are drawn with `QPainter` by `drawIcon` in `icons.go`; there are no image files. The same icons are shown before each request's name in the Requests tree. A new request type needs an entry in `requestTypes` and `typeLabels`. The top level of the tree is headings, not folders: `groupFolders` (`requestgroups.go`) lists each top level folder under gRPC or REST if its requests, at any depth, are all of that type, or under Mixed (with the folder icon) if they are not, in that order and only where there are some, with the folders that hold no requests after the headings on their own. This is worked out on every `draw` and recorded in `requestTree.top`, and never kept in the store, so a change that can move a folder to another heading must redraw (`remove` does, selecting the `neighbour`). A heading is not a folder: it is bold, at the left edge with no arrow (the tree's root is not decorated, so the folders under it have their arrows where a top level item would), always open, and cannot be selected (a click on it is ignored and the arrow keys pass over it), renamed, dragged or dropped onto. `locate` gives nil for both folder and request for it, so check the folder before using it. Do not give it `DontShowIndicator`, which makes Qt treat it as having no children, hiding its folders from the view. Its name is not searched. `requestTree` maps tree items to the store by position (`locate`), through `top` at the top level, so the two must be kept in the same order: under a folder's item come its folders, then its requests, which is why a new subfolder is inserted before the requests. Tests find top level folders with `topFolder` / `topCount`, which look under the headings. Beneath the search box is a tab bar (`requestTree.views`: `viewAll` / `viewFavourites`) over the one tree: with Favourites chosen (`requestTree.favourites`) `draw` lists only the favourite folders, under the same headings, and the search applies to whichever is shown. At startup (`requestTree.startView`, from `NewWindow` before the tabs are restored) Favourites is chosen if there are any, and Requests otherwise. The tabs have icons (`drawViewIcons`, drawn again by `Window.applyColours`): the folder of the Requests tab of the sidebar, and the filled star. `selectRequest` (which choosing a request tab and `restoreTabs` use) switches to Requests when the request is not among the favourites shown, so it is always seen selected. `draw` reports whether what it was to select is shown, and `reveal` (used after adding, importing, duplicating and moving) goes back to Requests (the tab of every folder) when it is not. The tree has a second column (`colStar`, of fixed width) for the star in the colour of favourites (`colourFavourite`, `starIcon`, filled for a favourite and in outline otherwise), which `hover` shows only on the folder under a heading (`starred`) that the pointer is over, from the tree's mouse move and viewport leave events; a press on it (`toggleFavourite`) is taken by the tree's mouse press event and selects nothing. `draw` forgets `hovered`, as its items are replaced. Add Folder and Add Request act on the selected folder, or the folder of the selected request; with nothing selected (or a heading), Add Folder adds a folder at the top level and Add Request makes a new top level folder, "New Folder", to hold the request, never using one already there; clicking empty space in the tree clears the selection, which is how a top level folder is added. Folders and requests are moved between folders by dragging (where exactly in a folder something is dropped makes no difference, as the order is alphabetical): the tree's drop event is intercepted, the move is made in the store (`Store.MoveRequest` / `MoveFolder`) by `requestTree.drop`, and the tree is redrawn from the store (`draw`) once the drag has finished, so Qt never moves items itself.
  - The search box above the Requests tree (`requestTree.search`) narrows it as text is typed: `applySearch` hides the items that do not match and opens the folders left, without touching the store, so items still map to it by position. Something matches when every word typed is in its name or the names of the folders above it, ignoring case. While a search is on, folders opened and closed are not recorded; clearing it redraws from the store, which puts them back. `draw` reapplies the search, and adding or importing clears it so the new item can be seen. Ctrl+1, Ctrl+2 and Ctrl+3 (`Window.focusSidebar`, `QShortcut`s) show the Workspaces, Environments and Requests tabs with the keyboard in the list or tree, leaving the selection alone. Ctrl+P (`Window.quickOpen`, a `QShortcut`) shows the Requests tab with the keyboard in the search box, and Return there (`requestTree.browse`) moves it to the tree, at the first request found, or where the selection is if nothing is searched for. A key which moves the selection in the tree does not open what it moves to (`requestTree.browsing`, set around the tree's own handling of the key, which is what makes left close a folder and right open one); Return opens the selected request, or opens or closes the selected folder (`activate`). Selecting with the pointer, or from code, still opens a request.
  - The URL field and the preview that takes its place are `wrapEdit`s (`wrapedit.go`): a `QTextEdit` kept to one paragraph, which wraps a long URL and is made as tall as its text (`fit`), since a line edit cannot wrap. It has the `Text` / `SetText` of a line edit and reports through `onChange` (only when the text really differs, as recolouring is reported as a change too) and `onReturn`. Its placeholders are coloured through `placeholderHighlighter.document`. What is beside it in the line stays level with its first line.
  - The URL field shows the enabled params as its query string and the two are kept in step both ways (`urlChanged` / `paramsChanged`, using `rest.SplitURL`, `JoinURL` and `MergeParams` in `rest/query.go`). The stored `rest.Request.URL` has no query string; the params hold it.
  - Loading a REST request, or changing its method, selects the tab it is likely to need (`requestPanel.showLikelyTab`, with the tabs named by `tabBody` / `tabParams` / ...): Body for POST, PUT and PATCH, and Params for the rest.
  - `requestPanel.request()` and `load()` are the only places widgets are converted to and from a `rest.Request` (likewise `grpcPanel` and `rpc.Request`); a new field must be added to both, to an `onChange` hook, and to the request's `Expand` so placeholders work in it.
  - Widgets report changes through callback fields (`onChange`, `onOpen`, ...) and use an `updating` flag to suppress them while being filled programmatically.
  - `Window.send` and `Window.invoke` apply the active environment with `Expand`, given one `Window.expander()` for the whole request (`Window.expand` is for the previews and the colouring of placeholders, which are not sent), and hand the work to `Window.run`, which gives it the time limit of the settings (`Window.timeout`, for every kind of request; `Window.options` gives a REST request that and whether to follow redirects, and `requestPanel.options` gives the curl command the same), runs it in a goroutine, returns to the GUI thread with `mainthread.Start`, and turns the button into Cancel while in flight. Results that arrive after another request has been shown are dropped (`Window.shown`). The status bar at the bottom of the window is not used for requests or responses; `Window.status` is only for problems loading or saving the data files. The Response tab of a response panel holds only real bodies (the HTTP body, or the gRPC messages); no hints or progress text go in it. Everything else about a response goes in the bar beneath it as labelled fields (`responsePanel.setFields`): Status (the HTTP status, or the gRPC code such as `5 NOT_FOUND`), Error (the gRPC status message, or the error there was instead of a response), Time, and Size and Protocol or Messages. Status and Error are at the left of the bar and the rest right-aligned. The left is a rich text table, so that a long error wraps beneath itself and not beneath the status. Values that are failures are in the colour of errors, red by default: an HTTP status of 400 or more, a gRPC status other than OK, and any error.
  - `Window.reflect` loads the service definition for the gRPC panel in the background and caches it per target in `Window.schemas`. It runs when a gRPC request is opened, when the server address or TLS setting changes, and on Reload (which bypasses the cache). `grpcPanel.setSchema` fills the method drop-down and keeps the saved method selected. Loading is silent; only a failure is reported, in the panel's status line. The drop-down is a `methodCombo`, which lists short method names under unselectable service headings and shows the full name when closed; read it through `current()`, not the combo's own text and index (the tests have a `selectMethod` and a `count` for it). The Service Definitions tab is an `endpointTable` (`endpoints.go`, `grpcPanel.endpoints`), also filled by `setSchema`: the short names of the methods under a heading row for each service, each with a checkbox, none ticked to begin with, and a page with a hint in its place while there are none. Beneath it are a button which ticks them all, or none if they all are (`toggle`), and Create Requests, which gives the ticked methods to `onCreate`: `Window.createRequests` makes a folder named after the server address with `endpointFolder` (a folder for each service, holding a gRPC request named after each method with the address of the request on show and nothing else of it: no message, metadata or authorization, and TLS off) and adds it to the top level with `requestTree.adopt`, which importing uses too. A request that is in such a collection edits it instead: `Window.endpointCollection` gives the folder holding the folder the open gRPC request is in, when that inner folder is named after a service of the server (the name of the outer one is never looked at), and `Window.syncEndpoints` (after `setSchema`, and from `requestTree.onSave`, which is called on every change to the store) gives the table the methods it has requests for (`endpointsOf`: gRPC requests in a folder named after the service of their method) through `endpointTable.setExisting`. Those are ticked and cannot be unticked, so requests are only removed in the sidebar; the button reads Update Requests, `onCreate` is given only the methods the user ticked (`added`), and `createRequests` adds them to that collection alone with `addEndpoints` and `requestTree.extended`, leaving the request on show. The toggle acts on the methods that can be ticked and are on show. Above the table is a search box (`endpointTable.search`), like the one above the Requests tree: `applySearch` hides the rows of the methods which do not have every word typed in their full name, ignoring case, and the heading of a service with none left; rows are hidden and not removed, a hidden method stays ticked, and the search is applied again to whatever is listed next.
  - Both the request tabs of the REST panel and the tabs of each response panel have a button, or a row of them, at the right of the line the tabs are on, made by `newIconButton` and `newButtonTabs` in `tabbutton.go`. It is the corner widget of the tab widget, which is given no more than the height of the tabs, so `newButtonTabs` uses its own `QTabBar` whose `tabSizeHint` makes the tabs as tall as the button. The request's button, curl, swaps the fields (`requestPanel.pages`: `pageFields` / `pageCurl`) for the request as a read-only curl command with Execute, Copy and Close buttons; as the tabs and so the button are not on show then, Close (or Escape) is the way back. `requestPanel.updateCurl` makes it from `request()` with the active environment applied (`requestPanel.expand`, set by the window) (through `requestPanel.expander`) using `rest.Request.Curl`, which is built on `Request.Build` so the command sends what Send would; it is refreshed when a request is loaded and when the environment changes. A request that cannot be built is shown as a `#` comment. The Execute button beside the command (`Window.executeCurl`) runs the request the command on show was made from (`requestPanel.commanded`, so that a value made by a function is the one shown) with the installed `curl` program through `rest.RunCurl`, which passes the same options without a shell, reads the status and headers from a `--dump-header` file and returns a `rest.Response`, so the result goes through `Window.run` and the response panel like any other; the button becomes Cancel while it runs.
  - Between the URL field and Send is the preview button (`requestPanel.preview`, an action button with an eye), which swaps the field (`requestPanel.urlPages`: `urlPageEdit` / `urlPageResolved`) for a read-only line showing the URL with each placeholder replaced: by its value in the active environment, in the colour of placeholders that are found, or where it has none (not defined, or defined as an empty value) by a black square (`missingValue`, U+25A0) in the colour of those that are not (`wrapEdit.setPieces`). `requestPanel.updatePreview` refreshes it when the request is loaded or edited and when the environment changes.
  - Escape closes whatever is open in place of the request (`Window.escape`): the environment editor, or else the bar of a search of the response, or else the curl command, or else the URL preview (`requestPanel.escape`). It is handled in the window's key press event, not as a shortcut, so that it only arrives when the widget with the keyboard has no use for it and still cancels the editing of a name or a cell.
  - The last button beside the tabs of a response panel is Save. It (`responsePanel.saveBody`) writes the body of the response to a file the user chooses: `responsePanel.content`, set by `setContent` whenever a response is shown, which is a JSON body formatted as it is shown, any other HTTP body as received, or the gRPC messages as shown. The button is disabled when there is no body. The name offered for the file is made by `saveFileName` from the name of the open request (`responsePanel.requestName`, set by the window; `untitled` if it is not saved), the time (`responsePanel.now`), `resp` and the extension for the content type: lower case, with an underscore for each run of anything but letters and digits, as in `book_room_20261011_173005_resp.json`. Tests replace `responsePanel.chooseSave`, `now` and `warn` rather than let dialogs open.
  - Before Save is the find button, which shows the bar text is found in the response with (`findBar` in `find.go`, `responsePanel.find`) above the body, inside the Response tab (`tabResponse`); Ctrl+F (`Window.find`, a `QShortcut`) does the same for the response panel on show, and Escape or the bar's own button closes it, ahead of anything else Escape closes on a request page. `findAll`, which is pure Go, gives the matches as `span`s in UTF-16 code units, as Qt counts positions. ## UI tests

`internal/ui/ui_test.go` has a `TestMain` that creates the `QApplication` offscreen and runs the Qt event loop on the main thread while tests run on another goroutine. A test that hangs is killed by `-timeout` (`go test ./internal/ui/ -v -timeout 90s` names it). Tests must pass `NewWindow` the `Files` of `testFiles(t)`, whose settings file names the keys made in `TestMain` (a test which makes its own `Files` or settings file needs `saveTestKeys` or `PublicKey: testPublic, PrivateKey: testPrivate`, as a window without keys loads nothing, and `closeWindows(t)` after its folder is made, which `testFiles` calls: it closes the windows when the test ends, as one left open saves its settings when the tests are over, into a folder that has gone, and says that it could not), read what a window saved with `loadEnvs` / `loadRequests`, which decrypt with those keys (`testFiles(t).Files`; its `Environments` and `Requests` are the paths of the files of the one workspace it makes, named Default), replace `requestTree.confirm` and `envList.confirm` (asked before an environment is removed) rather than let a modal dialog open, set `testRequestType` (or use `addGRPCRequest`) to choose the type of an added request, use `waitFor` for asynchronous results, create and touch widgets inside `mainthread.Wait` / `mainthread.Wait2`, never call `t.Fatal` inside them when the test goes on to wait for something (it ends the goroutine of the Qt main thread's callback, and the run hangs), and poll for asynchronous results rather than blocking the main thread.

## Commands

```sh
make build                # go build -ldflags "-s -w" -o triggerapi . (binary is gitignored)
make run                  # build, then ./triggerapi
make vet                  # go vet ./...
make test                 # go test ./...
go test ./path/to/pkg -run TestName   # single test
```

Releases for Linux are an AppImage, built by `.github/workflows/appimage.yml` (on a `v*` tag, which makes a release, or by hand) in an `ubuntu:22.04` container, so that it runs on glibc 2.35 and later; glibc itself is not bundled. The Qt of that system (6.2) is too old for the bindings, so the workflow installs Qt's own build (`QT_VERSION`, with aqtinstall, into `/opt/qt`) and points `PKG_CONFIG_PATH`, `LD_LIBRARY_PATH` and `QMAKE` at it. `packaging/appimage.sh` (`make appimage`) does the work with linuxdeploy and its Qt plugin, asks for the Wayland plugins as well as the xcb ones that come by default, copies in Qt's GTK platform theme (`platformthemes/libqgtk3.so`, which the tool leaves out and without which a dark GNOME desktop gets light windows; GTK itself is the desktop's own and is not bundled, so where it is missing or does not suit the bundled libraries the plugin is not loaded and Qt carries on without), refuses to make an AppImage without any of these, and starts what it made offscreen to check that it runs, from `packaging/triggerapi.desktop` and `packaging/triggerapi.png`, with `packaging/AppRun` as what the AppImage runs (a script, not the link to the program the tool would make, which newer versions of Qt do not find their plugins through). Where the system's folder of Qt plugins has those of a desktop as well (anything not named `lib*.so`, such as KDE's), the script bundles from a copy with only Qt's own, through a `qmake` wrapper which names the copy. Under Wayland a window has no icon of its own unless the desktop supports the `xdg-toplevel-icon` protocol and Qt is 6.9 or later, which is why the AppImage has at least that Qt; otherwise the icon is that of an installed desktop file named after `QGuiApplication_SetDesktopFileName` (`triggerapi`, set in `main.go`). The PNG is the one image file there is: it is `appIcon()` saved at 256 pixels, and has to be made again if the icon is changed.

Always build the binary without debug symbols (`-ldflags "-s -w"`), either with `make build` or by passing the flags to `go build`.

Smoke-test the GUI without a display:

```sh
QT_QPA_PLATFORM=offscreen timeout 3 ./triggerapi   # exit code 124 means it started and kept running
```

Running it reads and writes the user's real settings and workspaces, so run the smoke test from a scratch directory with the configuration and data folders pointed there too (`cd "$(mktemp -d)" && XDG_CONFIG_HOME="$PWD/config" XDG_DATA_HOME="$PWD/data" QT_QPA_PLATFORM=offscreen timeout 3 /path/to/triggerapi`).

## Building with miqt

- miqt is cgo: building needs a C++ compiler and the Qt 6 development headers (found via `pkg-config`, e.g. `Qt6Widgets`).
- The first build of `github.com/mappu/miqt/qt6` compiles the whole binding and takes about 5 minutes; later builds use the Go build cache and are fast. Use a long timeout for the first build, and avoid `go clean -cache` or changing cgo flags, which forces the full rebuild.
- That build prints a large volume of `-Wsfinae-incomplete` warnings from the Qt headers. They are noise; search the output for `error` instead of reading it.
- Linux is the only tested platform for now (the README has untested macOS build instructions using Homebrew). A macOS release is planned, so avoid adding Linux-only assumptions (paths, shell-outs, X11/Wayland specifics) where a portable Qt or Go API exists.
- `README.md` lists the packages needed to build on each distribution; keep it in step if the Qt modules used change (currently only `Qt6Widgets`).

## miqt conventions

- Import as `qt "github.com/mappu/miqt/qt6"`. Use the `qt6` package, not `qt` (which is Qt 5).
- C++ overloaded constructors and methods become numbered Go functions (`NewQMainWindow2()`, `NewQLabel3("text")`). Check the miqt package source or docs for the right overload rather than guessing the number.
- Static methods are `Class_Method` (`qt.QApplication_Exec()`); signals are connected with `OnSignalName(func(...))`.
- Qt widgets must only be touched from the main (GUI) thread. Network calls run in goroutines and hand results back with `mainthread.Start` from `github.com/mappu/miqt/qt6/mainthread`.
- Memory: objects from `NewQ...` constructors are never freed by Go, so short-lived ones need `Delete()`. Value types returned by methods and static functions (`ToQVariant()`, `QFontDatabase_SystemFont()`, ...) already have a finalizer (`GoGC()` in the miqt source); calling `Delete()` on those is a double free that crashes at a later garbage collection. Check the generated function before deleting anything.
- Do not use methods that return a Qt value type by value rather than by pointer, such as `QPlainTextEdit.FirstVisibleBlock()` and `BlockBoundingGeometry()`: miqt returns a copy of a struct whose C++ object is freed when the original is garbage collected. Use an equivalent that returns a pointer (`CursorForPosition(...).Block()`, `CursorRect(...)`).
- A finalizer runs on a thread of the garbage collector, not the GUI thread. That crashes for a `QTextCursor` (`TextCursor()`, `CursorForPosition(...)`), which is on the list its document keeps of its cursors: being taken off it from another thread while the GUI thread changes the document corrupts the heap. Free every text cursor a method returns with `release` (`release.go`), which removes the finalizer and deletes it at once. `TestTextCursorsWhileCollecting` covers this.
- Pass a widget to a layout or container through its embedded base (`button.QWidget`, `layout.QLayout`, `window.QObject`).
